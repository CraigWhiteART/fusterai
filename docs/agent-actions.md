# Shopify actions (approval and unattended)

Phases 9-10. The agent can **propose** order actions; code decides whether each one waits for a human or runs unattended within limits the owner set. Nothing is enabled on install: every action's policy is `never` until an admin changes it.

> **Status: none of this has run against a real Shopify store.** Mutations, inputs and scopes were checked against the Shopify Admin GraphQL schema and shopify.dev docs for API version **2026-10** (see "Shopify API notes"), and every path is covered by tests with `Http::fake`. Before enabling any unattended policy, follow the dev-store script at the end.

Code: `app/Domains/Commerce/Actions` (registry, policy, executor, HTTP), `routes/agent_actions.php`, `config/agent_actions.php`, migration `2026_11_29_500000_create_agent_action_tables.php`. Tests: `tests/Feature/Commerce/Actions`.

## How a proposal flows

1. The writer calls `propose_action {action, order_number, reason, details, params}` (params are structured, see "Actions"). The tool records it on the run and rejects, with a reason the writer sees:
   - `rejected_unknown_action`, `rejected_not_allowed` (not in the playbook's `allowed_actions`),
   - `rejected_unavailable` (Shopify not connected, or a required access scope is missing),
   - `rejected_disabled` (resolved policy is `never`, the default),
   - `rejected_invalid_params` (the errors are returned so the writer can fix them and call again).

   A `proposed` action adds a ledger fact `action.proposed.<key>.<n>` (its plain-English description, incl. amount / discount code). That grounds "I've arranged a refund of AUD 20.00" in the deterministic validator, and the reply is held until the action succeeds (reply coupling below). The discount code is generated by the system, never by the model.
2. For a **live** run, `RunEffects` makes one call: `ActionRecorder::recordForRun($run, $conversation)`. Each `proposed` entry becomes an `agent_action_executions` row; the run's `proposed_actions[i]` gets `execution_id` and `execution_status`. Non-live runs throw (they never reach the recorder).
3. The recorder reads the order fresh from Shopify (read-only), checks preconditions, resolves the policy and evaluates limits:
   - policy `never` / scope missing: `cancelled` with the reason,
   - every unattended condition holds: `approved` (`route = unattended`) and `ExecuteActionJob` is queued,
   - otherwise: `pending_approval` (`route = approval`) with `approval_reasons[]` and `expires_at`. Never dropped silently. A sender-email mismatch also hands the conversation over (internal note, `conversations.handover_reason = action:sender_email_mismatch`).
4. A human approves (optionally editing params, re-validated) or rejects (reason required; recorded as a `rejected` feedback event with `meta.reason = action_rejected`).
5. `ExecuteActionJob` (`tries = 1`) runs the executor (below).

An identical proposal (same conversation, action, canonical params, order) reuses the existing row (unique `idempotency_key`), so regenerating a draft never queues the same refund twice.

## Actions

Keys match `config('agent.actions')` (what playbooks list in `allowed_actions`). "Money" actions need the money approver role and always require the sender to match the order email. "Reply waits" = a draft that uses it is not sendable until it succeeds.

| Key | Shopify call | Scopes | Money | Reversible | Reply waits | Unattended possible |
|---|---|---|---|---|---|---|
| `add_order_note` | `orderUpdate(input: {id, note})` (current note + appended line) | `write_orders` | no | yes | no | yes |
| `tag_order` | `tagsAdd` / `tagsRemove` on the Order id | `write_orders` | no | yes | no | yes |
| `change_address` | `orderUpdate(input: {id, shippingAddress})` | `write_orders` | yes | yes (by hand) | yes | yes, 4PX guard |
| `cancel_order` | `orderCancel(orderId, reason, restock, notifyCustomer, refundMethod, staffNote)` | `write_orders` | yes | **no** | yes | yes, 4PX guard + hard ceiling |
| `refund` | `Order.suggestedRefund` (read) then `refundCreate(input) @idempotent(key)` | `write_orders` | yes | **no** | yes | yes, hard ceiling |
| `discount_code` | `discountCodeBasicCreate` (verify: `codeDiscountNodeByCode`) | `write_discounts` | yes | yes (deactivate) | yes | yes |
| `replacement` | `draftOrderCreate` (100% discount, free shipping, tagged) then `draftOrderComplete` | `write_draft_orders`, `read_orders` | yes | **no** | yes | **never** (approval only) |
| `fulfilment_hold` | `fulfillmentOrderHold` (handle = execution marker) / `fulfillmentOrderReleaseHold(holdIds)` | `write_merchant_managed_fulfillment_orders` or `write_third_party_fulfillment_orders` | no | yes | no | yes |

There is no `escalate_to_human` action: the writer's existing `handover` tool does that.

### Params (`params_hint` in the catalogue; validated server-side)

- `add_order_note`: `{note}` (2-500 chars).
- `tag_order`: `{add: [tag], remove: [tag]}` (at least one; tags `[A-Za-z0-9 _:-]`, max 40 chars, 5 each).
- `change_address`: `{first_name?, last_name?, company?, address1, address2?, city, province_code?, zip, country_code (ISO-2), phone?}`.
- `cancel_order`: `{reason: CUSTOMER|INVENTORY|OTHER, restock: bool, refund: bool, notify_customer: bool}` - all explicit, none defaulted. Refund goes to the original payment method(s).
- `refund`: `{line_items?: [{line_item_id: "gid://shopify/LineItem/..", quantity, restock?}], amount?: "20.00", shipping: none|full|amount, shipping_amount?, notify_customer: bool, reason}`. Line items **or** amount (or shipping only). With line items Shopify computes the amount (`suggestedRefund`); `restock` only for unfulfilled units (restock type `CANCEL`), otherwise `NO_RESTOCK`.
- `discount_code`: `{template, value?, customer_specific? (default true), code (system)}`. Templates are admin settings; `value` may not exceed the template's `max_value` nor the hard maximum (50%). Usage limit 1, once per customer, expires after the template's `expires_days` (max 90), optionally limited to the order's Shopify customer.
- `replacement`: `{line_items: [{line_item_id, quantity}], reason}` (same variants, at most the ordered quantity).
- `fulfilment_hold`: `{operation: hold|release, reason (hold): OTHER|INCORRECT_ADDRESS|AWAITING_RETURN_ITEMS|HIGH_RISK_OF_FRAUD|INVENTORY_OUT_OF_STOCK|UNKNOWN_DELIVERY_DATE, note}`. Exactly one open fulfilment order; release removes only holds fusterai placed.

### Preconditions (checked fresh, before approval and again right before the mutation)

- every action: order found; for money/address actions the approval card shows a danger warning when the sender's email (customer or Reply-To) does not match the order email.
- `change_address`, `cancel_order`: not cancelled, no fulfilment recorded, `displayFulfillmentStatus` in UNFULFILLED / ON_HOLD / OPEN / PENDING_FULFILLMENT / SCHEDULED. Country change is a warning (and blocks unattended).
- `refund`: `Order.refundable`; paid in the shop currency (presentment = shop currency); each line item quantity <= `refundableQuantity`; restock only for unfulfilled units; total > 0; **total <= min(suggestedRefund.maximumRefundableSet, the parent payment's maximumRefundableV2, netPaymentSet)**; exactly one successful SALE/CAPTURE can cover it (split payments are refunded by hand).
- `discount_code`: template still exists; order has a Shopify customer when `customer_specific`.
- `replacement`: line items exist with a variant; quantity <= ordered; original has a shipping address.
- `fulfilment_hold`: fulfilment orders readable; exactly one open; release needs a fusterai hold.

## Policy

`agent_action_policies`: `(workspace_id, action_key, playbook_id nullable)` unique, `mode` `always | approval | never`, `limits` json, `override_workspace` bool. **No row = `never`.**

Resolution (`PolicyResolver`):

1. Workspace row (playbook_id null), else `never`.
2. A playbook row can only make it **more restrictive**: stricter mode wins (never > approval > always), numeric limits take the lower value, lists intersect, `require_sender_email_match` ORs. Exception: an admin sets `override_workspace = true` on the playbook row, which then replaces the workspace row.
3. Code rules on top: `replacement` is never unattended (an `always` policy is downgraded and the API refuses to save it); money/address actions always have `require_sender_email_match = true` (the API refuses `false`).

Limits (all optional):

| Limit | Meaning |
|---|---|
| `max_amount` | Max per action (shop currency). Required for refund / cancel / fixed discount to run unattended (`no_max_amount_limit`). |
| `per_customer_30d_amount`, `per_customer_30d_count` | Rolling 30 days, same action, same customer email, statuses approved / executing / succeeded / unknown. |
| `per_day_amount`, `per_day_count` | Since midnight (app timezone), same action, whole workspace. |
| `max_percentage` | Discounts; required for percentage discounts to run unattended. |
| `max_order_age_days` | Order age window. |
| `allowed_fulfilment_states` | `displayFulfillmentStatus` values allowed. |
| `allowed_countries` | ISO-2 shipping countries (current and, for address changes, the new one). |
| `require_sender_email_match` | Default true; mandatory for money/address actions. |

Hard rules regardless of policy: refunds and refunding cancellations above `agent_action_settings.refund_hard_ceiling` (default AUD 150, never above `config('agent_actions.max_refund_ceiling')`) are approval-only; replacement is approval-only.

**Unattended** = policy `always` AND agent mode `live` AND kill switch off AND the run drafted (did not hand over) AND sender email matches the order email AND fresh preconditions pass AND every limit holds AND the workspace daily cap `agent_settings.caps.actions_per_day` has room (default 0 = nothing unattended) AND, for address change / cancel, the 4PX guard clears. Each failed condition becomes an `approval_reasons` code (labels in the API).

Permissions are human-only: policies and settings are written only by `ActionPolicyController` (admins). The writer's tools only read them; proposals strip permission/limit ops (`OpsApplier`, `ProposalApplier`); a test fails if any other file writes them.

### Who approves

`agent_action_settings.approver_role_money` (default **admin**) for refund / cancel / address / discount / replacement; `approver_role_other` (default **agent**) for notes, tags and holds. The approver must also be able to view the conversation. Rationale: with two staff (the owner and one colleague), irreversible money actions default to the owner, who carries the financial risk; low-risk internal actions can be done by either. The owner can set `approver_role_money` to `manager` or `agent` to let the colleague approve refunds.

## The 4PX problem (open business decision)

Once an order has been pushed to the 4PX warehouse, changing its address or cancelling it in Shopify may not reach the warehouse. Until the owner provides a rule, `change_address` and `cancel_order` may run unattended only when **all** hold:

- the order is unfulfilled (no fulfilment, status UNFULFILLED / ON_HOLD / OPEN / PENDING_FULFILLMENT / SCHEDULED),
- no fulfilment order has `requestStatus` SUBMITTED / ACCEPTED / CANCELLATION_REQUESTED / CANCELLATION_REJECTED or `status` IN_PROGRESS / INCOMPLETE (i.e. nothing is with / accepted by a fulfilment service),
- fulfilment orders could be read (needs a `read_*_fulfillment_orders` scope; without it the answer is "unknown" and the guard fails),
- the order is younger than `agent_action_settings.unattended_order_age_minutes` (default 60).

Otherwise the action is approval-only (`approval_reasons` contains `warehouse_guard`) and the card's first warning (level `danger`) says the warehouse may already have the order, with the signals found. The window is configurable; 4PX may pull orders through its own app without any Shopify fulfilment request, so a short window is the main protection. **Owner: decide the real rule** (e.g. "never change address after X; email 4PX first").

## Executor

```
proposed --record--> pending_approval --approve--> approved --claim--> executing --> succeeded
                 \-> approved (unattended) ------------^             |--> failed   (userErrors / request refused; hand over)
                 \-> cancelled (never / no scope)                    |--> unknown  (timeout / 5xx / connection; reconcile)
pending_approval --> rejected | expired                              |--> pending_approval (unattended, but a limit/precondition no longer holds)
approved --> cancelled (kill switch / policy now never / scope gone / non-live dry run)
unknown --reconcile--> succeeded | failed (only after two empty looks) | stays unknown -> hand over after N attempts
```

- **Claim before any request.** `approved -> executing` is a conditional UPDATE; a second job or a double click sees 0 rows and exits. Approve/reject are conditional too (`pending_approval -> ...`), so a second approve gets 409.
- **Fresh state, re-evaluated.** The executor reads the order again, re-checks preconditions, scopes and policy. Human-approved actions whose preconditions no longer hold stop as `failed` ("the order changed since approval") and hand over. Unattended ones whose limits no longer hold go back to `pending_approval`.
- **Never retried blind.** `tries = 1`. Timeout / connection error / 5xx / errors alongside data => `unknown`; `ReconcileActionJob` re-queries after `reconcile_delay_seconds` (60) up to `reconcile_max_attempts` (5): it looks for the execution marker (`fusterai-action-<id>`) in refund notes, the order note, draft-order tags, hold handles, or checks the address / tags / `cancelledAt` / discount code. A "not there" is only believed on the second look (a slow read must never make a done refund look undone). After the last attempt it hands over: "check Shopify before doing anything by hand". Refunds additionally carry Shopify's `@idempotent(key)` (required since 2026-04) derived from the execution.
- **userErrors** => `failed`, internal note with Shopify's message, `conversations.handover_reason = action:user_errors`.
- **Success** => `verify()` re-reads Shopify; if not visible yet => `unknown` + reconcile (orderCancel runs as a Shopify job). Then: audit line appended to the order note naming the helpdesk and approver (`agent_action_settings.audit_note`, default on; result in `verify_result.audit_note`), undo info, spatie activity log (`log_name = agent-actions`), broadcast.
- **Kill switch / pause / mode, checked twice.** When the job starts, the kill switch cancels any approved execution. Immediately before the mutation (after the fresh Shopify reads) it is checked again: an **unattended** execution stops for anything in `AutoSendGuard::autonomyBlockedReason()` (kill switch -> cancelled; mode not `live` or auto-sending paused -> back to `pending_approval` with `agent_mode_not_live` / `autonomy_paused`); a **human-approved** one stops only for the kill switch (cancelled). Approve returns 409 while the kill switch is on.
- **Dry run for every non-live purpose.** `ShopifyGatewayFactory` returns `DryRunShopifyGateway` (no HTTP client at all) unless the execution and its run are `live`. The recorder throws for non-live runs; an approved non-live row is cancelled with `dry_run = true`. Tests assert `Http::assertNothingSent()` for preview / simulation / shadow / test.
- Secrets: stored `request` / `response` / snapshots are passed through `Redactor` (credential-looking keys and `shpat_/shpca_/...` tokens). The access token is only ever in the request header.

## Reply coupling

`App\Domains\Commerce\Actions\ActionGate`:

- `ActionGate::blocksSending(AgentRun $run): bool` - the seam for auto-send / `SendReplyJob`.
- `ActionGate::state($run)` => `{state: ready|waiting|needs_rewrite, blocking: [execution ids], failed: [ids], executions: [{id, action_key, status, reply_blocking}]}`.
  - `waiting`: a reply-blocking action is pending / approved / executing / unknown, or a live run has a reply-blocking proposal that was never recorded (fail closed).
  - `ready`: none, or all succeeded.
  - `needs_rewrite`: one failed / was rejected / expired / was cancelled. On failure or rejection (once per execution, only if that run is still the conversation's latest live run, agent in draft/live, kill switch off) a regenerate is queued (`GenerateReplySuggestionJob`, `regenerate: true`); the new run's evidence contains the outcome (`ActionOutcomeEvidence`: facts `action.<status>.<key>.<id>` plus a note "it has NOT happened").

- **Auto-send** waits for the actions a reply depends on and turns back into a draft if any needs a human or fails ([agent-autosend.md](agent-autosend.md#replies-that-depend-on-an-action)).
- **Human sends**: the composer / API reply refuses a message while `blocksSending` is true for the current draft's run, unless the person edited the text and confirmed `send_anyway: true` (`ReplySendGuard`, [agent-api.md](agent-api.md#sending-a-reply-while-the-draft-waits-on-a-shopify-action)).

The deterministic validator fails a draft that claims a completed action ("I have refunded / cancelled your order / updated your address / sent a replacement / created a discount code / put your order on hold") unless the ledger has `action.proposed.*` (this run) or `action.succeeded.*` for that action (a still-pending action from an earlier run does not count: this reply would not wait for it) (check `claimed_action`).

## Shopify API notes (verified against docs / schema, API 2026-10)

- Version: `config('commerce.shopify_api_version')` = `2026-10` (latest stable; 2025-01 is past its support window and was being served by Shopify's oldest supported version). `ShopifyClient::MIN_API_VERSION` raises older stored versions. Read queries were updated for 2026-10: `Customer.email` -> `defaultEmailAddress { emailAddress }`, `ShopPlan.displayName` -> `publicDisplayName` (parsing accepts both).
- `refundCreate`: `RefundInput {orderId, note, notify, refundLineItems [{lineItemId, quantity, restockType}], shipping {amount | fullRefund}, transactions [{orderId, parentId, kind: REFUND, gateway, amount}]}`; `@idempotent(key:)` optional from 2026-01, required from 2026-04. `Order.suggestedRefund(refundLineItems, refundShipping, shippingAmount)` returns `amountSet`, `maximumRefundableSet`, `shipping {amountSet, maximumRefundableSet}`.
- `orderCancel` returns `job` + `orderCancelUserErrors` (not `userErrors`); irreversible; asynchronous.
- `orderUpdate` is the documented way to change the shipping address; `orderEditBegin` is for line items / quantities / discounts.
- `tagsAdd` / `tagsRemove` accept an Order id.
- `discountCodeBasicCreate(basicCodeDiscount: DiscountCodeBasicInput)`: `context` is a oneOf (`customers {add}` or `all: ALL`); `customerGets {value {percentage | discountAmount {amount, appliesOnEachItem}}, items {all}}`; `DiscountUserError`.
- `draftOrderCreate` / `draftOrderComplete` (`write_draft_orders`).
- `fulfillmentOrderHold(id, fulfillmentHold {reason, reasonNotes, handle, notifyMerchant})`, `fulfillmentOrderReleaseHold(id, holdIds)`; FulfillmentOrder `status` / `requestStatus` enums as used by the 4PX guard; reading fulfilment orders needs a `read_*_fulfillment_orders` scope.
- Scopes: a write scope includes its read scope; `read_orders`/`write_orders` cover the last 60 days; `read_all_orders` extends either (no Shopify approval needed for a Dev Dashboard app in the merchant's own organisation).
- Client-credentials tokens carry every scope granted to the installation (the `scope` parameter is ignored), expire after 24h, and work only for stores in the same organisation. They are app tokens, so the "user must have permission" notes in the docs do not apply.

Sources: shopify.dev/docs/api/usage/versioning, shopify.dev/docs/api/usage/idempotent-requests, the 2026-10 reference pages for refundCreate, orderCancel, orderUpdate, tagsAdd, discountCodeBasicCreate, draftOrderCreate/Complete, fulfillmentOrderHold/ReleaseHold, FulfillmentOrder, Order (incl. the 60-day note), shopify.dev/docs/api/usage/access-scopes, shopify.dev/docs/apps/build/authentication-authorization/access-tokens and .../client-credentials-grant, plus the Admin GraphQL schema introspection tool.

### Not verified (treated conservatively)

- `orderCancel` with `refundMethod` omitted is assumed to refund nothing (we always send it explicitly when refunding).
- With line items, `suggestedRefund.amountSet` is assumed to include the shipping portion requested; the refund total sent is that amount.
- `RETURN` restocking needs a location; we only restock unfulfilled units (`CANCEL`) and refuse otherwise.
- `@idempotent` with an inlined literal key (as in Shopify's examples) rather than a variable.
- Whether a Shopify-side address change or cancel reaches 4PX (the open business decision above).
- How quickly refunds / cancellations become visible to a re-query (reconcile waits and needs two empty looks).
- Protected customer data: outside dev stores Shopify may redact order emails until the app is approved for protected customer data; with a redacted email every money action fails the sender match and goes to approval.

## Dev-store test script (owner)

1. In the Shopify Dev Dashboard, open the app > Versions > create a version with access scopes: `read_orders, write_orders, read_all_orders, read_customers, read_products, write_discounts, write_draft_orders, read_third_party_fulfillment_orders, write_third_party_fulfillment_orders, read_merchant_managed_fulfillment_orders, write_merchant_managed_fulfillment_orders`. Release it and approve the update on the **dev store**.
2. In fusterai: Agent > Connections > "Test connection" (records the new scopes). `GET /agent/actions/catalogue` should show every action `available: true` and no `read_all_orders` advisory.
3. Settings: `PATCH /agent/actions/settings` with a discount template, e.g. `{"discount_templates": [{"key": "sorry10", "label": "Sorry 10%", "type": "percentage", "value": 10, "max_value": 10, "expires_days": 30}]}`.
4. Put every action on **approval** (`PUT /agent/actions/policies/{key} {"mode": "approval"}`) and add the keys to one test playbook's `allowed_actions`. Agent mode `draft`.
5. On the dev store place test orders (Bogus Gateway) from an address you can email from. For each action, send a customer email that asks for it, check the card (description, amounts, warnings), approve once, then confirm in Shopify admin: note line, tags, new address, cancellation (+ refund), refund (amount, notification), discount code (single use, expiry, customer), replacement order (100% off, free shipping), hold placed and released. Also try: approve twice quickly (one effect), reject (draft gets rewritten), an email from a different address (sender-mismatch warning + hand-over), a refund above the refundable amount (stops before sending).
6. Only after every action worked with approval, and the owner has decided the 4PX rule: set `agent_settings.caps.actions_per_day` (e.g. 5), give one low-risk action (`add_order_note` or `tag_order`) an `always` policy, agent mode `live`, and watch the audit log (`GET /agent/actions/audit`) for a week before enabling any money action unattended with tight limits (`max_amount`, `per_customer_30d_count: 1`, `per_day_amount`).
